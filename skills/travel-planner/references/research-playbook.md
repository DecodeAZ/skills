# 信息采集与行程编排手册

本文件承接正文中"采什么、怎么判断、什么情况下必须改方案"的领域规则。正文只保留流程骨架。

## 一、目的地推荐四阶段

目的地未知时，先筛选再规划。阶段间有严格依赖，不得跳步：

| 阶段 | 输入 | 输出 | 可并行 |
|---|---|---|---|
| A 候选发现 + 季节 + 人群 | 区域范围、月份、人员 | 候选短名单（3-5 个） | 按区域并行 |
| B 交通可行性 | A 的短名单 | 可行性排名 | 与 B2 并行 |
| B2 天气预检 | A 的短名单 | 各候选地降雨天数 | 与 B 并行 |
| C 综合对比 | B + B2 | 排名与推荐理由 | 依赖前两者 |

用户给的是区域（如"广西""云南"）而非具体城市时，必须先检索候选地，不得凭一般知识预设。

### 淘汰规则

- 出行期内降雨天数 >= 50% → 标记"天气风险高"，在阶段 C 降权。
- 带婴幼儿或老人时连续降雨 >= 3 天 → 建议优先排除。
- B2 仅在出发日距今 <= 16 天时执行（Open-Meteo 预报上限 16 天）；超过 16 天按气候均值参考并标注"历史同期均值，非预报"。

### 交通耗时判据

| 单程耗时 | 判断 |
|---|---|
| <= 4h | 理想，不占用游玩时间 |
| 4-6h | 可接受，占用半天 |
| 6-8h | 勉强，带婴幼儿或老人需谨慎 |
| > 8h | 行程 < 7 天时不推荐 |

## 二、季节性陷阱检查

每个候选地都要核对：核心吸引物在出行时段是否处于最佳状态。

| 类型 | 要查的事 | 反例 |
|---|---|---|
| 瀑布 / 水景 | 是否枯水期 | 德天瀑布 4 月枯水，7-11 月最佳 |
| 花海 / 红叶 | 花期叶期是否匹配 | 薰衣草 6 月未开，7 月中旬才盛 |
| 海滩 | 是否台风季、禁渔期 | 台风季出海项目常停运 |
| 雪景 / 滑雪 | 是否已化雪 | 3 月下旬雪道多已关闭 |
| 温泉 | 是否旺季爆满 | 冬季周末需提前订 |

## 三、特殊人群适配

### 婴幼儿（0-3 岁）

- **推车友好度**：景区路面是否平整可推车，是否有台阶、石板路、湿滑路段。
- **母婴设施**：当地超市是否有奶粉与尿不湿，酒店是否提供婴儿床。
- **医疗距离**：距最近有儿科的医院多远。
- **安全风险**：是否有深水区、陡崖、湿滑台阶。
- **节奏适配**：是否适合慢节奏，是否有午休条件。

### 老人

- 海拔高反风险；避免海拔 > 3000m 的景点，除非预留适应期。
- 无障碍设施与医疗可及性。
- 每日步量控制在 1.5 万步以内，安排午休。

## 四、衔接验证清单

涉及转机或转高铁时必做。车次与时刻优先用 `flyai search-train` 取（返回真实车次号，比通用搜索可靠），票价仍以 12306 为准。对每个"A 交通 → B 交通"的转换节点确认：

1. **A 的到达时间** 与 **B 的末班时间** —— 是否来得及。
2. **A → B 的转场方式与耗时** —— 机场到火车站的距离、打车/地铁/大巴各需多久。
3. **缓冲是否充足** —— 落地后取行李再转场，至少预留 1.5 小时。

不可行时的三条出路：

- 改更早的航班；
- 到达城市住一晚，次日再转；
- 机场直接包车或租车到目的地，跳过火车。

行程中必须显式标注衔接风险，例如"末班高铁约 21:00，建议选 17:00 前落地的航班"。

## 五、价格可靠度分级

每项费用都要标注等级，不得混用。

| 等级 | 含义 | 标注方式 | 示例 |
|---|---|---|---|
| 实查 | 权威平台（12306 / 景区官网）或 FlyAI 机票 `ticketPrice` | 无标注 | 高铁票¥34、FlyAI 机票¥1327 |
| 参考 | FlyAI 的酒店 / 门票 / 火车票档位价，以及检索所得的起步价、区间、往年价 | 价格后加 `~` | 酒店~¥600/晚 |
| 估算 | 无直接数据源，按同类经验推断 | 价格后加 `≈` | 市内打车≈¥500 |

### FlyAI 各字段可用度（实测 2026-09-13；2026-10-05 复测）

| 接口 | 字段 | 实测形态 | 可标等级 |
|---|---|---|---|
| `search-flight` | `ticketPrice` | 精确值 `"1327.00"`（10/10） | 实查 |
| `search-hotel` | `price` | 脱敏档位 `"¥6xx"`（6/6；复测 10/10） | 参考 |
| `search-poi` | `ticketInfo.price` | 空 28 / 脱敏 `"¥2x"` 4 / 精确 1（复测 10 条中仅 1 条有值） | 参考 |
| `search-train` | `price` | 脱敏档位 `"9xx"`、`"4xx"`（10/10） | 参考 |
| `search-poi` | `poiLevel` | 复测仅 2/10 有值 | 缺失时留空 |
| `ai-search` | `data` | **自然语言字符串（Markdown）**，不是 itemList | 需单独适配，勿按结构化解析 |

酒店与景点均无评分字段（`rate`、`score`、`rating` 实测全为 null），不要输出评分或"住客评分"类表述。

### 信封判定（唯一可信的成功信号）

FlyAI 每个子命令都返回同一个信封，**进程退出码不可信**——业务失败仍以 0 结束。判定顺序固定：

| 观察 | 结论 | 处置 |
|---|---|---|
| `status == 0` 且 `data` 非 null | 取数成功 | 解析 `data.itemList` |
| `status == 0` 且 `data` 为 null（常见 `message=empty`） | **查询成功但无结果** | 记为"该条件无结果"，换条件或降级；**不是故障，不要重试** |
| `status != 0`（如 `出发日期非法`、`CICO_CHECK_PARAM_ERROR`） | 业务失败 | 按 `message` 修参数；同类错误重复出现说明参数生成逻辑有误，不要原样重试 |
| 退出码非 0、stdout 非 JSON | 命令本身失败 | 看 stderr：`unknown command` / `required option` 属调用方式问题；含 403/429 属风控 |

实测样本（2026-10-05）：`search-flight --dep-date 1999-01-01` → 退出码 0、`{"data":null,"message":"出发日期非法","status":1}`；不存在的景点关键字 → 退出码 0、`{"data":null,"message":"empty","status":0}`。两者的处置完全不同，只看退出码会把它们混成一个"成功"。

**禁止行为**：把通用搜索得到的区间价写成"实查"；把 FlyAI 的脱敏档位写成精确报价；在没有 FlyAI 结果时声称取到了实时报价；把 `data:null` 当成"查到 0 条"或"查到有数据"。

## 六、计费口径

- 婴儿机票（2 岁以下）约成人票价 10%；婴儿高铁免票。
- 4 名以上成人通常需 2 间房。
- 餐饮按人均 × 人数 × 餐数；婴幼儿不单独计餐费。
- 门票：1.2m 以下或 6 岁以下通常免票，需按目的地逐条核实。

## 七、行程编排原则

1. **地理聚类**：相近景点排同一天，减少无效通勤。
2. **节奏交替**：暴走日后接休闲日。
3. **就近用餐**：餐厅选在当日景点附近。
4. **弹性时间**：每天留 1-2 小时缓冲。
5. **到达日轻松**：第一天只安排入住与周边。

婴幼儿场景额外约束：每日最多 2 个景点（上午 1 + 下午 1）；13:00-15:00 不安排活动或安排车程；逐景点标注是否需要推车或背带；餐厅优选有儿童座椅或空间宽敞的。

## 八、缓存与 TTL 口径

每次生成行程都重打一遍接口是当前最大的浪费，也是 FlyAI 风控的根因。**所有外部请求前先查缓存。**

| 项 | 约定 |
|---|---|
| 位置 | 用户工作目录 `[目的地]-[年-月]/.cache/`，与产物同目录，便于随行程归档。**不写进技能仓库** |
| 键 | `源 + 规范化参数 + 查询日期`，参数需归一化（城市名去空格、坐标保留 2 位小数） |
| TTL | 天气 30 分钟；POI / 坐标 24 小时；车次时刻当日；价格 30 分钟；静态资产（12306 站名表、城市坐标）长期 |
| 范围纪律 | 只缓存本次行程相关的最小片段；**高德原始地理数据不落盘**；OSM 派生数据若落盘须保留署名 |

静态资产可显著减少运行期请求：12306 站名表（`kyfw.12306.cn/otn/resources/js/framework/station_name.js`，实测 200 / 169KB）与常用城市坐标表都可本地化后长期复用。

**缓存必须容错（重复调用场景）**：

| 情形 | 处置 |
|---|---|
| 文件缺失 | 正常未命中，取数后写入 |
| 解析失败 / 空文件 / 结构不符 | **按未命中处理并整条覆盖重写**，不中断流程，不采信半截数据 |
| 命中且未过期 | 直接复用，不再发请求；同一行程内同一键重复命中不做二次请求 |
| 已过期 | 重新取数，整条覆盖；不做增量合并 |
| 写入中断 | 用"先写临时文件再改名"的方式落盘，避免留下半截 JSON 被后续误读 |

缓存条目属于用户数据，随行程目录归档；**不写进技能仓库，也不誊抄进交付正文**。

**限速**：FlyAI 串行 + 间隔 ≥ 3 秒 + 批内去重，单次行程总额 ≤ 40 次；命中风控后退避 ≥ 45 秒并把间隔放宽到 ≥ 12 秒。

## 九、多源 POI 去重规则

POI 与坐标不再单源依赖。合并规则：

1. **坐标优先**：距离 < 100m 视为同一实体。
2. **名称相似度**：坐标接近时再看名称，含包含关系（"西湖" ⊂ "杭州西湖风景名胜区"）直接合并。
3. **字段补全而非覆盖**：门票是否计入门票预算一律以 FlyAI 的 `freePoiStatus` 为准；评分、营业时间只在高德侧有值时补入。
4. **来源标记**：每条 POI 记录来源（`flyai` / `amap` / `osm`），交付时按来源决定是否带署名。

坐标来源优先级：Open-Meteo Geocoding（城市级）→ FlyAI `latitude`/`longitude`（POI 级）→ Nominatim（免 Key 备源）→ 高德（可选，GCJ-02，**不落库**）→ Overpass（尽力而为，15 秒超时即放弃）。

## 十、各源署名与合规

用到哪个源就附哪一条，未使用的不要写。

| 源 | 署名 / 合规口径 |
|---|---|
| Open-Meteo | 数据 CC BY 4.0，署名 `Weather data by Open-Meteo.com`；非商用 < 1 万次/日；商用需订阅或自托管 |
| FlyAI | 飞猪 MCP；按 `detailUrl` 引导去飞猪 / 携程落实 |
| 和风天气 | 署名「数据由和风天气提供」；Key 只本地配置，不入仓库、不进产物 |
| 高德 | **不得存储原始地理数据**；需实名；商用需授权；坐标 GCJ-02 |
| OSM / Overpass / Nominatim | ODbL，署名 `© OpenStreetMap contributors`；派生数据库 share-alike；公开实例 fair use，建议 < 1 万次/日、**不并行**、带可识别 User-Agent |
| 小红书 MCP | 平台 ToS 与账号风险，用户自担 |
| 12306 | 无官方开放 API，社区实现仅研究用途；票价以官方为准 |
