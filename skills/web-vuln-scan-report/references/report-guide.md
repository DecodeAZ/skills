# 报告结构与写作规范

模板：`assets/report-template.html`（13 章，占位符 `{{...}}`）。产出物放目标项目的 `reports/` 或用户指定路径。

## 13 章固定骨架

| 章 | 内容 | 可省略 |
|---|---|---|
| 01 | 结论摘要：KPI + 一句话结论 + "比 CVE 更值得先看的 N 件事" | 否 |
| 02 | 技术栈测绘：接入层 / 前端 / 后端三张表，每行带证据 | 否 |
| 03 | 风险分布：按包条形 + **按适用面重归类**（仅 Node / 需 PP / 浏览器） | 否 |
| 04 | 修复优先级：P0(24h)/P1(一周)/P2(两周)/P3(规划) 卡片 | 否 |
| 05 | 依赖漏洞明细：逐条 CVE 表（编号/CVSS/等级/摘要/影响面/修复版本） | 无命中时可并章 |
| 06 | 网关人工比对（nginx 等） | 无网关 CVE 时可省 |
| 07 | 非版本类问题：F-01 起，finding 块（证据/影响/建议 dl 结构） | 否 |
| 08 | 未覆盖范围与盲区 | 否 |
| 09 | 如何进一步获取后端信息（方法+工具+执行清单） | 建议保留 |
| 10 | 离线产物深度分析（API 攻击面/路由/实时通道/凭据存储） | 无产物时省 |
| 11 | 本地工具链实测（环境/工具表现/交叉验证/新发现/复现命令） | 建议保留 |
| 12 | 修复方案与整改建议（总览矩阵 + 分级落地 + 验收 + 残余风险） | 否 |
| 13 | 附录 · 探测证据（原始请求响应、扫描范围、免责声明） | 否 |

## 发现编号与定级

- 按 F-01、F-02… 顺序编号，跨章连续（第 7/10/11 章的发现共用一个序列）。
- 等级用 HIGH/MEDIUM/LOW/INFO，另加状态标签：`待确认`（需服务端联调）、`需验证`（CSWSH 类）。
- CVSS 保留漏洞库原值，但叙述必须按第 3 章适用面重判；严禁拿 9.9 分直接说"本站可被利用"。
- 每个发现三要素齐全：**证据（可复现的请求/响应）→ 影响（业务语言）→ 建议（指向第 12 章条目）**。

## 证据与脱敏

- 进入报告前所有证据过 `http_client.mask`：IP 末段 → `1.2.3.x`，32 位 hex → `<uuid>`；坐标类手动截断。
- 附录保留原始命令与响应（脱敏后），这是报告可信度的来源；无证据的推断写进"盲区"而不是正文结论。
- 探测请求统计要写明：总请求数、方法、速率、时间窗——让对方能确认"只读、量小"。

## 语言规范

- 中文；每个结论可复现：`curl`/脚本命令 + 预期输出。
- 好话也要写：防护到位的点（403 拦截、HSTS、无 sourcemap）单独列"正面信号"。
- 不确定的事写"待确认/需联调"，标注在发现上而不是含糊带过。
- 打印友好：模板已含 `@media print`，交付前 Ctrl+P 过一遍 PDF。
