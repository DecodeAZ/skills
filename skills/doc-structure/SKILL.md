# 文档结构初始化及检查

一套经过实战验证的项目文档布局（源自 classes_hub 项目），本技能做两件事：
**初始化**（为新项目搭建骨架）和 **检查**（审计现有项目文档是否完整、一致）。

## 目标结构

```
<项目根>/
├── README.md              项目简介 + 文档索引表（链接 docs/ 每个主文档）
└── docs/
    ├── 01-架构设计.md      总体架构、分层、数据策略、已知限制
    ├── 02-功能特性.md      功能特性、页面/路由表
    ├── 03-使用指南.md      使用指南：启动、主流程
    ├── 04-接口文档.md      API 参考（端点分组表、协议、错误码）
    ├── 05-配置说明.md      配置项唯一全表
    ├── 06-部署流程.md      部署流程：本地 / Docker / CI
    ├── 07-开发指南.md      开发指南：环境、代码结构、测试、脚本
    ├── modules/           每个代码模块一份设计文档（<模块名>.md）
    ├── manual/            用户操作手册（可按角色分：教师端/学生端…）
    ├── plans/             工作计划，文件名以日期前缀：YYYY-MM-DD-<主题>.md
    ├── specs/             设计规格，文件名：YYYY-MM-DD-<主题>-design.md
    └── reference/         调研报告、测试报告、评估报告
```

分层的道理：顶层七件是"任何项目都有"的通用文档；modules/ 与代码结构一一映射，
改代码时知道改哪份文档；plans/specs 用日期前缀保证时间线可追溯；reference/
存只增不改的历史材料，避免污染正式文档。

### 主文件命名约定

docs/ 顶层主文件**优先按 `0x-中文名称.md` 样式生成**：两位数序号按上表顺序，
使目录列表顺序即推荐阅读顺序；中文名称可微调但关键词保持可识别
（架构 / 功能 / 使用 / 接口或 API / 配置 / 部署 / 开发），
且关键词应紧跟序号置于名称**开头**（如 `04-接口文档.md`）——脚本按
「去掉序号前缀后以关键词开头」识别主文档，`GHSA镜像部署.md` 这类前缀式
补充文档不会被误认成主文档（否则 deployment 类被它顶替而漏报，2026-10-26 实测教训）。
旧项目已用英文名（architecture.md、API.md 等）视为等价，检查时不报缺失，
也不要求改名。modules/ 下例外：文件名沿用代码模块名（与代码对应优先于编号）。

## 工作流 A：初始化

项目还没有（或只有零星）docs/ 时执行：

1. 创建上述目录骨架，主文件按"主文件命名约定"以 `0x-中文名称.md` 生成。
   只建目录和确有内容的文件——空文件不如不建，
   骨架阶段各主文档写入一段真实的项目相关引言（读 README 和代码目录后总结，
   不要写占位废话）。
   docs/ 已有散落文档时先归位：调研 / 报告 / 规范类迁入 reference/（只增不改），
   操作性内容并入对应主文档；迁移后在 README 索引登记，不留双份。
2. 若代码已有明确模块（如 `backend/app/<模块>/`），为每个模块在
   docs/modules/ 建一份文档，含：模块名标题、职责、代码位置、后续补全标记。
3. 在根 README.md 末尾建立（或补齐）文档索引表：

```markdown
## 文档索引

| 文档 | 内容 |
| --- | --- |
| [docs/01-架构设计.md](docs/01-架构设计.md) | 总体架构与已知限制 |
| [docs/02-功能特性.md](docs/02-功能特性.md) | 功能特性、页面路由表 |
| [docs/03-使用指南.md](docs/03-使用指南.md) | 使用指南 |
| [docs/04-接口文档.md](docs/04-接口文档.md) | API 参考 |
| [docs/05-配置说明.md](docs/05-配置说明.md) | 配置项全表 |
| [docs/06-部署流程.md](docs/06-部署流程.md) | 部署流程 |
| [docs/07-开发指南.md](docs/07-开发指南.md) | 开发指南 |
| [docs/modules/](docs/modules/) | 模块设计：<逐个列出并链接> |
```

文档多时索引表分「主文档 / 模块设计 / 参考」三小节各一张；reference/ 按惯例
可不进索引，但补上更友好（脚本对 reference/ 不做孤儿检查，进不进都不报）。

4. 七件之外的补充文档（如 `数据流程图.md`、`管理接口.md`）延续编号排在其后
   （`08-数据流程图.md` …），自由中文名也可以，但七件主文件优先用编号样式。

## 工作流 B：检查

对现有项目执行五类检查，先跑脚本拿确定性结果，再用人工判断补齐：

### 第 1 步：跑确定性脚本

```bash
bash <技能基目录>/scripts/check_docs.sh <项目根>
```

技能基目录即本 SKILL.md 所在目录（ZCode 加载技能时会显示 Base directory）；
脚本不依赖安装位置。本技能为纯 bash 实现，无 Python / pip 依赖，
依赖与降级策略见 `skill-dependencies.json`。

脚本报告：目录布局缺失、README 断链、应索引区域（docs/ 顶层（含 .html）+
modules/ + manual/）中未被 README 索引的孤儿文档、plans/specs 文件名缺日期前缀。
这些是机器可判定的，直接采信。plans/、specs/、reference/ 是历史档案，
按惯例不进 README 索引，脚本不检查它们的覆盖率。
输出里「-」开头的是问题（计入退出码），「·」开头的是提示不是问题：
manual/plans/specs/reference 未建属预期（空目录不如不建），
不要为消提示而建空目录。

### 第 2 步：模块文档覆盖核对（人工）

列出代码实际模块（按布局选：`ls src/<包名>/*/`、`ls backend/app/*/`、
前端 `web-ui/src/views|components`、monorepo 逐包），与 docs/modules/*.md 对比：
代码有模块但无文档 → 报告缺失；文档有模块但代码已删
→ 报告过期。模块名对不上（重命名、合并）比单纯缺失更常见，逐一确认。

### 第 3 步：README 索引质量（人工）

索引表每一行的"内容"描述与文档实际首段是否相符；文档刚大改过而索引描述没跟上,
是常见的漂移点。

### 第 4 步：文档间引用一致性（人工）

docs/ 内部互相链接的文档（如 modules/*.md 引用 ../API.md）链接目标是否还存在;
脚本只查 README，docs 内链需抽查近期改动过的文件：
`grep -rn "](.*\.md" docs/ | grep -v "](http"` 后逐个验证。

### 第 5 步：输出报告

按此格式汇总，先结论后细节：

```markdown
## 文档结构检查报告：<项目名>

结论：完整 / 有 <N> 处需修复（<断链 x、索引缺失 y、模块缺文档 z、命名不符 w>）

| 类别 | 问题 | 位置 | 建议 |
| --- | --- | --- | --- |
| 断链 | docs/old.md 不存在 | README.md:42 | 删除或改指 docs/new.md |
| 索引缺失 | docs/reference/报告.md 未被索引 | — | 补入索引表 |
| 模块缺文档 | backend/app/cache/ | — | 建 docs/modules/cache.md |
| 命名 | plans/下周计划.md 无日期前缀 | — | 改 2026-10-26-下周计划.md |
```

用户要求修复时才动手改；只报告时不要顺手改文件。

## 参考文件

| 文件 | 用途 |
|---|---|
| `scripts/check_docs.sh` | 确定性检查：目录布局 / README 断链 / 索引覆盖率 / plans+specs 日期前缀命名；退出码 0 = 通过，1 = 有问题，2 = 目录不存在 |
| `skill-dependencies.json` | 依赖清单与功能降级映射（bash 运行时 + 包内检查脚本） |

## 判断边界

- 脚本查不出的语义问题（描述与内容不符、文档已过期）靠读首段判断，别全量精读。
- plans/ 里的"待优化功能清单""待实现功能清单"这类无日期文件是有意为之的活文档,
  命名检查时豁免，不要报它们违规。
- 「缺少 docs/manual|plans|specs|reference」类提示不用处理：可选分区有内容再建，
  脚本里它们以「·」开头、不计入问题数。
- 检查范围不含 node_modules、.git、虚拟环境、缓存目录。
